Problem & Requirements

DK Aviation runs two ADS-B ground stations on different firmware. They needed one queryable, enriched, near-real-time dataset with audit traceability — without standing up infrastructure.

Technical requirements

  • Event-driven ingest from S3
  • Two JSON schemas — flat vs nested array
  • 15-minute freshness SLA
  • Source file + row number on every record
  • Join to FAA registration data

Business requirements

  • One unified view across stations
  • Answer "who owns this aircraft, what model?"
  • Audit-ready lineage
  • Minimal warehouse spend
  • Near-zero operational overhead

The Snowflake Concepts That Made This Work

Six features carry the entire solution — no external tooling, no servers.

Snowpipe

Event-driven auto-ingest. An S3 → SQS notification triggers the load the moment a file lands. Serverless, billed per file.

VARIANT + FLATTEN

Store raw JSON natively with no load-time schema; LATERAL FLATTEN unnests arrays at query time. This is what absorbs the two firmware formats.

Dynamic Tables

The whole pipeline in one CREATE: define the SQL, set TARGET_LAG = 10 min, Snowflake owns scheduling, incremental refresh and state.

Streams + Tasks

The imperative alternative — CDC on a table plus scheduled SQL, gated on SYSTEM$STREAM_HAS_DATA. More control, more objects.

METADATA$ columns

METADATA$FILENAME and METADATA$FILE_ROW_NUMBER deliver the traceability requirement with zero custom code.

Stages & External Tables

A Storage Integration gives secure IAM access to S3; external tables query the bucket in place with partition pruning, no copy.

Why it matters: every requirement maps to a managed platform feature. There is no ETL server, scheduler, or CDC tool to operate.

Architecture — Ingest, Transform, Serve

The whole pipeline is six objects and no infrastructure. Data never leaves the customer's S3 until Snowpipe pulls it; the conformed layer is one declarative Dynamic Table; auditors get read-only views on their own XSmall warehouse, so their queries can never contend with ingestion.

Ingestion: Two Options, Compared

Use Stream + Task when…

  • Conditional logic or multi-step DAG
  • Needs a stored procedure call
  • Execution must hit an exact window

Use Dynamic Table when…

  • Transform fits one SELECT
  • Freshness is an SLA, not a schedule
  • You want less to operate
My recommendation — Dynamic Table. Our conformed layer is flatten + cast + join FAA on ICAO hex: a single SELECT. The control Stream + Task buys has nothing to control here. Same 15-min SLA, 4 objects down to 1, backfill and refresh history for free.

POC observation: the 509M vs 59M row gap isn't a bug — the Dynamic Table backfilled all history automatically; the streams only saw rows inserted after creation. That gap is the argument.
